# Project pane ownership refactor

## Acceptance criteria and boundary

The change addresses the project-pane finding in the component/pane coupling audit. The pane must retain its exact shell, controls, labels, tab IDs, list/Kanban behavior, permissions, project/short IDs, save delay, and request policy. It must stop owning project editing, organization moves, and work-item persistence in one component. No data cleanup, migration, product behavior change, or runtime performance improvement is claimed.

`ProjectPanelView` now composes three independent owners: overview editing, organization/properties, and work-item presentation. Their hooks run unconditionally for the original pane lifetime. Moving them into the lazily mounted tab bodies or conditionally mounted properties rail would change initialization, pending edits, and request lifetimes, so that alternative was rejected. The hooks return owned content rather than exposing all internal state/setters to the host. They reuse the host translation function, preserving its single translation subscription.

The work-item list source now belongs to `ProjectManager/WorkItems/hooks/useProjectWorkItemsSource.ts`. `applyWorkItemUpdate` centralizes UI-patch conversion, the empty-patch guard, and the canonical partial-update request across that source, `useWorkItemsData`, and the aggregate work-item interaction owner. Reconciliation stays with each source because one stores enriched rows, one stores UI rows, and one preserves aggregate project metadata.
