# App memory metrics architecture audit

Scope: Issue #435 native app-memory snapshot, WebView ownership, Tauri wire
contract, shared frontend store, Sidebar, and Settings diagnostics.

## Completion checklist

- [x] One authoritative byte-based App memory snapshot.
- [x] Top total includes only ORG2 backend and safely owned WebView helpers.
- [x] macOS resolves active WebKit service PIDs from the current ORG2
      process bootstrap namespace before using the conservative observation fallback.
- [x] Ambiguous macOS/Windows ownership is excluded and reported as partial.
- [x] Terminal, CLI agent, MCP, and tool RSS stays in a separate wire type.
- [x] Sidebar and Settings share one in-flight request and snapshot store.
- [x] Old heuristic child-process command, wire type, tests, and UI callers removed.
- [x] All WebView creation entry points swept and covered.
- [x] Serialized v1 payload inspected by a Rust wire-contract test.
- [x] Rust and frontend full library/unit suites, TypeScript, targeted lint,
      and changed-file formatting pass.

## Term overloading table

| Term                | Canonical meaning                                                                          | Rejected meaning                            |
| ------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------- |
| App memory          | Effective bytes for ORG2 backend plus owned WebView helpers                                | All descendants; terminal/tool RSS          |
| RSS / mapped        | Diagnostic sum in `rss_mapped_total_bytes`                                                 | A native effective-memory label             |
| Tool process        | Descendant shown only by the RSS diagnostic command                                        | A member of the App memory boundary         |
| Partial attribution | At least one relevant helper could not be safely attributed, or the ownership query failed | An estimate that may include unrelated apps |

## Systematic sweeps

- `WebviewWindowBuilder::new|WebviewBuilder::new`: every repository hit was
  classified and wrapped; Windows native popup `Allow` is covered by environment
  enumeration instead of a host builder.
- `get_child_processes_memory|ChildProcessInfo|memory_metric_kind`: zero legacy
  production hits remain.
- `getAppMemoryTotals`: both user-visible totals call the same selector.
- All settings locales contain the new measurement labels. Attribution remains
  an internal wire-state signal by product decision; no visible warning copy is
  required.

## Platform verification note

The macOS unit suite runs the native physical-footprint code and rejects a
Safari-style executable path as a trusted candidate. Parser and ownership tests
also verify that active WebContent/GPU/Networking service PIDs are included,
unlisted Safari/other-app WebKit processes are excluded, and role mismatches
produce partial attribution. The latest isolated live dev run resolved the
current ORG2 host to exactly one WebContent, one GPU, and one Networking helper.
Direct `footprint --pid` measurements were approximately 61 MiB backend,
502 MiB WebContent, 19 MiB GPU, and 9 MiB Networking (about 591 MiB total),
within the agreed acceptance tolerance. The Windows API subset
(EX2 counters, Private Bytes, process creation time, and WebView2 process-info
enumeration) cross-compiles for `x86_64-pc-windows-msvc` in an isolated check.
The full workspace cannot cross-compile from macOS because existing unrelated
build scripts attempt host Objective-C and MSVC assembly work for the Windows
target; native Windows runtime validation remains part of release QA.
