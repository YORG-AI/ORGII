# Harness connections architecture audit

Scope: local Claude Code and Codex API connections, shared Settings/detail UI, cc-switch import metadata, and the existing native configuration transaction boundary. This is one feature, with no session-runtime rewrite or cloud configuration changes.

| Layer                         | Evidence and decision                                                                                                                                                                                                                                                                                                       |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 — Compilation               | Rust application check and TypeScript native typecheck pass; owning-crate tests exercise configuration and resolver behavior. Exact final verification is recorded in the PR                                                                                                                                                |
| 2 — Ownership and duplication | Settings and Claude/Codex detail both call HarnessConnectionEditor → typed RPC → harness_connections commands → key_vault resolver → agent_cli transaction. Other harnesses retain their existing managed adapters                                                                                                          |
| 3 — Names                     | `Direct` is a distinct CliConfigMode, while `OrgiiManaged` keeps its existing proxy meaning. Existing managed_config module remains the owner of native profile transactions                                                                                                                                                |
| 4 — Semantics                 | A vault connection is credential/endpoint/model data; a harness configuration is machine-local exported state; a receipt is temporary test evidence. None is represented as a running session                                                                                                                               |
| 5 — Defaults                  | Direct is the initial route; reopening an existing proxy configuration retains that route. Unsupported agents, auth methods, models and protocols return errors. No account fallback is introduced                                                                                                                          |
| 6 — Boundaries                | key_vault resolves secrets without returning them in status; agent_cli handles native files without importing vault or frontend state. App commands own version checks, HTTP testing and receipt lifecycle                                                                                                                  |
| 7 — Discoverability           | Settings manifest, segment registry, rendering slot, and CLI detail wiring lead to the shared editor. User-facing recovery and scope are documented in docs/harness-connections.md                                                                                                                                          |
| 8 — Wire                      | Status sends key IDs, names, models, endpoint, compatibility reason and config hashes, never API keys. Test sends synthetic echo-tool requests with no workspace content. Loopback fixtures inspect native CLI Authorization and model values; protocol tests inspect tool-result identifiers and terminal streaming events |
| 9 — Entry parity              | Settings/detail share the same RPC path. Direct and proxy use the same resolver. The old managed command also checks third-party receipts. The fixture example invokes the real direct file writer but intentionally bypasses vault/version/UI validation with synthetic data; it is not production UI E2E evidence         |
| 10 — Resolver symmetry        | Credential/provider/model/endpoint resolve from the same saved key. Model must be saved and enabled; endpoint uses the selected key override or the central provider default. Anthropic endpoint aliases are resolved in the same function for direct and proxy                                                             |

All ten layers reviewed. Cloud sync, session queue/FSM, mobile execution, OAuth refresh and new protocol translation are intentionally outside scope.

## State and recovery

Direct profiles persist across application shutdown. Managed profiles retain restore-on-exit behavior. Cross-process advisory locks cover the native paths and manifest; expected hashes from the UI are rechecked under lock. Transactions recheck before writing and after writing. Recovery restores only bytes known to belong to the interrupted transaction; independent external edits retain the journal and surface a conflict.

No database migration is introduced. The profile mode gains `direct`; transaction journals gain optional hash fields. Older application versions do not understand direct mode: restore the original setup before downgrading. Recovery of an old pending journal lacking hashes may require manual inspection rather than an unsafe automatic overwrite.

## Limits

An advisory lock coordinates ORGII writers, not unrelated editors. A noncooperating writer can still race between a hash check and atomic rename. Existing versioned backups are retained; automatic pruning is deferred because they may hold the user's only original credentials. Credentials exported in direct mode are snapshots: editing/deleting a vault entry does not revoke or automatically update them. Native project/profile/environment overrides and existing sessions may take precedence.

No upstream cc-switch code or SDK is linked or copied. The dependency additions are fs2 for portable advisory locks and the already-resolved toml_edit version for preserving Codex TOML comments.
