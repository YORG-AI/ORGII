# Settings search architecture review

Acceptance criteria: keep a permanently visible, left-aligned Settings-sidebar search; retain the top-bar Global Spotlight action; search localized settings controls globally across unmounted sections and tabs as well as canonical destinations such as “Skills, MCPs, Plugins”; update automatically as schema-backed options change; show no dropdown until the user types; support keyboard navigation; and navigate, reveal, and focus a selected control without duplicate opening flashes.

| Layer                         | Coverage and result                                                                                                                                                                                                                                                                                |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 — Compilation               | Full TypeScript compilation, targeted ESLint, and focused Vitest coverage. Tests prove all schema keys are indexed exactly once, localized appearance settings resolve while another page is mounted, MCP remains searchable, and delayed destination rows reveal and focus.                       |
| 2 — Dead code and duplication | Destinations continue to come from `buildSettingsNavigationGroups`; global controls are projected from `SETTINGS_REGISTRY`. A small override table contains only UI-name/route exceptions, not a second list of settings. The current DOM scan remains solely for UI-only rows outside the schema. |
| 3 — Naming                    | `GlobalSettingsSearchItem` is a schema-backed cross-route result; `RenderedSettingsControl` is a live supplementary row snapshot; `SettingsNavigationItem` remains a page destination. `SettingsSidebarSearchItem.kind` keeps selection behavior explicit.                                         |
| 4 — Semantic overloading      | The dropdown deliberately combines destinations and controls, but each retains distinct ids, group ownership, and selection paths. Group headings provide context and are never treated as settings results. Global Spotlight remains a separate top-bar action.                                   |
| 5 — Defaults                  | Empty or whitespace-only input keeps the panel closed. Schema labels use localized keys where available and a deterministic humanized key fallback. Missing or dev-hidden navigation owners are omitted instead of producing broken routes.                                                        |
| 6 — Domain boundaries         | The canonical schema owns the set of persisted settings. `settingsSearch.ts` adds only search projection metadata for label or route exceptions. `SectionRow` publishes stable schema-key markers for destination reveal without owning navigation.                                                |
| 7 — Readability               | Data flow is linear: schema registry + canonical navigation + locale → global grouped index; optional active-page rows supplement it; shared filtering produces results; selection navigates once and resolves by schema key.                                                                      |
| 8 — Serialization             | Intentionally skipped: no persisted settings, JSONC format, URL contract, IPC, or network payload changed. Search ids and DOM attributes are presentation-only.                                                                                                                                    |
| 9 — Initialization parity     | The global catalog is built from every `getSettingsKeys()` result and the test asserts exact set parity. Declarative manifest rows pass `row.key` automatically; custom Appearance, code-editor, and chat rows declare the schema keys they render.                                                |
| 10 — Resolver symmetry        | Global items carry the same schema key published by destination `SectionRow` instances. Reveal checks target id, then schema key, then localized label, and uses a bounded observer only while a selected route is rendering.                                                                      |

The authoritative source is `SETTINGS_REGISTRY` for schema-backed settings and `buildSettingsNavigationGroups` for visible destinations and route ownership. The root cause was that the prior producing path started at the mounted DOM, so it could never represent controls on unmounted pages. The corrected producing path is schema registry → global localized search projection → dropdown result → route navigation → schema-key row reveal. Live DOM collection now supplements only UI-only rows on the active page.

The source-level invariant is that every schema key appears exactly once in the global search catalog whenever its owner destination is visible. New schema-backed settings are included automatically; the exception table is needed only when a visible row intentionally uses a different localization key or route than the schema convention. No stored settings or historical data changed, so no remediation or migration is required. Source rollback is a normal code revert.
