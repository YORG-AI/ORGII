# Branch picker lifecycle and architecture review

Both branch and PR tabs now use one virtual scrolling owner in Spotlight and the compact dropdown. It mounts a visible window plus five overscan rows per side, tracks actual row heights/gaps, resets the window after search, and scrolls to keyboard selections by index even when their DOM nodes do not yet exist. The compact branch list no longer does a full `findIndex` for each rendered row.

PRs load on demand in pages of 50, newest-updated first, with at most 10 pages / 500 retained rows per open picker. A user scroll near the end or the footer action requests the next page. Appending results does not automatically drain further pages. Search operates on loaded PRs, discloses that scope while more pages may exist, and does not trigger automatic page scans. Page errors retain loaded rows and require explicit retry. Duplicate PR numbers across shifting pages are merged, retaining the freshest returned payload.

Check status is read only from each list response’s `ci_status`. Both presentations use the same indicator and the existing metadata-enabled list command. There are no per-row check requests, new timers, or check caches. Concurrent picker consumers coalesce the entire list/enrichment operation by GitHub endpoint, credential identity, repository, and page. This is page-level deduplication within the picker, not a claim that differently sized list requests elsewhere in the app share the same response. GitHub errors or missing enrichment stay unavailable; they are not shown as passing or as no checks. Refresh/reopen/visibility return revalidates status with the list.

Branch metadata still comes from the existing full Git branch listing and shared cache, preserving complete local branch search. Its existing limit is 20 repository entries with a five-minute freshness policy; this change does not add a second branch-data cache or implement backend branch pagination. Virtualization bounds DOM rows, not the full branch metadata dataset. This is not a claimed hard heap cap for repositories with arbitrarily many refs.

The default-off “Show branch info” preference retains one boolean through the existing Jotai storage pattern. Only mounted PR pickers subscribe; closing them disposes their subscriptions. Toggling reprojects at most 500 retained PR rows, without requests, timers, new row caches, or changes to virtual row height. Both presentations continue searching the original PR metadata. A native checkbox target is excluded from the shared dropdown navigation handler so Enter cannot prepare/check out the highlighted PR.

No live PR checkout through the UI, history reset, schema migration, package/lockfile change, or historical-data cleanup was performed. Existing unrelated workspace edits were preserved. An already-started native operation cannot be canceled by closing the picker; it may finish creating a local branch, but this path never checks it out after unmount. Rolling back both frontend and native changes restores the earlier list behavior; no persisted data conversion is required. The optional `orgii-spotlight-show-branch-info` boolean defaults off and is ignored by older builds; deleting it resets the view preference without affecting repository data.

Performance verdict: blocked — automated correctness and DOM/request-bound evidence is available, but native visible/hidden/post-close CPU/RSS measurements, live GitHub checkout, and visual QA were not run because Computer Use requires explicit opt-in. The isolated feature worktree passes full TypeScript compilation. No native memory/frame-time improvement is claimed.
