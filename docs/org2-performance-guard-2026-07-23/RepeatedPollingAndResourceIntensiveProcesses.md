# Repeated Polling and Resource-Intensive Process Audit

- **Audit date:** 2026-07-23
- **Scope:** Production code under `src/` and `src-tauri/`
- **Method:** Static lifecycle and resource-retention audit using the ORG2 performance guard
- **Source changes:** None

## Executive summary

The audit identified several high-confidence performance failures alongside a larger set of bounded or feature-scoped recurring processes.

The highest-priority issues are:

1. Streaming sessions can rebuild and allocate a near-complete EventStore snapshot every 33 ms.
2. The work-item scheduler scans all projects and all work items every 30 seconds, with synchronous database work in an async task.
3. Work-item views poll complete message histories every 3 seconds and repeat Git/file calculations every 5–10 seconds.
4. Hosted-key activity, CSV drafts, approval details, navigation history, and several metadata maps have unbounded retention paths.
5. Every open PTY owns recurring reader and child-status polling, while frontend terminal caches are bounded mainly by entry count rather than total bytes.
6. Automation file watchers combine 200 ms polling with an unbounded event channel.
7. Frontend and backend diagnostics independently own recurring collection/flush schedulers.
8. Several feature pollers continue to wake while the document is hidden or have no maximum retry lifetime.

The most important architectural theme is that expensive work is often driven by elapsed time instead of authoritative invalidation. Several paths also use entry-count caps where byte-aware bounds are required.

## Scope and exclusions

Included:

- `setInterval`, recursive `setTimeout`, async loops, retry loops, heartbeats, long-polls, and watcher threads.
- Filesystem, database, Git, process, network, and model work initiated by recurring processes.
- App-lifetime and feature-lifetime caches, buffers, queues, maps, and snapshot stores.
- Large on-demand operations that can create significant CPU or RAM bursts.

Excluded:

- Unit, integration, E2E, and benchmark implementation timers unless they represented production behavior.
- One-shot UI debounces and bounded reveal/retry sequences.
- Development simulations that cannot run in production.
- Runtime CPU/RSS measurements; this is a static audit and does not claim measured impact.

## Low-cost repeated UI clocks and animations

The following processes are individually low-cost and generally component-scoped with cleanup, but many simultaneous instances can still create avoidable wakeups:

- One-second countdowns and elapsed-time displays in plans, questions, modes, process lists, title adapters, MCP rows, open-source countdowns, and download progress.
- Voice-recording elapsed time at approximately 250 ms.
- Streaming status HUD updates at approximately 500 ms.
- Kanban, replay, and simulator autoplay timers based on playback speed.
- Loading/stroke animations around 2.2 seconds.
- Development-only streaming simulations and API-call panel polling.

Shared clocks should be preferred where many copies can mount simultaneously. Nonessential clocks and animation work should stop when hidden.

## Recommended remediation order

1. Replace the 33 ms full EventStore snapshot build with incremental streaming deltas and incremental indexes.
2. Replace global work-item scans with indexed due-item queries and move blocking database work off async executor threads.
3. Replace work-item message/file/diff polling with push invalidation and cursor/delta queries.
4. Add hard byte limits and eviction to hosted-key activity, CSV/XLSX drafts, terminal output, approval details, navigation history, channel fragments, and merge buffers.
5. Consolidate terminal child/read polling and per-stream turn-index threads into shared or blocking notification mechanisms.
6. Remove duplicate diagnostics ownership and share system/memory snapshots between consumers.
7. Apply visibility-aware recursive scheduling to every noncritical frontend poller.
8. Add TTL/lifecycle pruning for blocked notifications, Git watcher metadata, agent live status, pinned session state, and server/channel caches.
9. Add performance regression tests for bounds, cleanup, non-overlap, hidden-state suspension, and repeated open/close cycles.
10. Perform runtime profiling in visible idle, hidden idle, active streaming, large-history, multi-terminal, and post-disposal scenarios.
